# CVY-013 Milestone Report — Live DAG and onchain dependency gate

**Date:** 2026-08-07
**Status:** DONE; reviewed and approved
**Commit:** this milestone commit

## Outcome

CVY-013 adds a live React Flow DAG to the run page and makes
`ConvoyRegistry.isCommitted(runIdOnchain, dependencyIdx)` a runtime precondition for every
dependency-bearing target write. The existing app-side gate remains authoritative for all declared
dependencies; the KeeperHub gate is an additional atomic read-and-conditionally-execute call.

## DAG flow

- `RunDetail` owns one append-only SSE connection and passes the same live item/event state to the
  Timeline and DAG tabs. Switching tabs does not create competing state semantics or freeze the DAG
  at the page snapshot.
- `DagView` renders one node per item and one `dependencyIdx → itemIdx` edge per declared dependency.
- Node colours use Timeline's chronological `deriveItemState` reducer.
- While a target is `DEFERRED` and a prerequisite has not reached `LANDED`, that edge is dashed,
  animated and opacity-pulsed. Live events remove the waiting treatment.
- Timeline and Manifest remain separate tabs with their existing behaviour.

## Execution flow

1. `releaseDeferred()` still releases an item only when **every** declared dependency is `LANDED`.
2. `executeItem()` submits `ConvoyRegistry.commitAction` through KeeperHub and records the COMMIT
   attempt.
3. The item advances only when the commit is `completed` and has a transaction hash. Any other real
   result moves the item to `FAILED` and blocks every target path, mitigating G-35.
4. A dependency-bearing item selects the lowest declared dependency index deterministically. The
   app-side gate has already checked the full dependency set; KeeperHub exposes one condition rather
   than an invented multi-condition capability.
5. One `check-and-execute` request reads
   `ConvoyRegistry.isCommitted(runIdOnchain, selectedDependencyIdx) == true`; its action is the
   dependent item's real target write.
6. A met condition supplies the target execution ID and continues through the existing SUBMITTED,
   polling, attempt, transaction-link, receipt/gas and LANDED flow. There is no subsequent
   `writeContractCall`, so the target is submitted once.
7. An unmet condition has no execution ID and performs no action. Convoy records the real condition
   fields and terminates the item as `FAILED`; it does not return it to `DEFERRED` and cannot loop.
8. Transient failures reuse the existing attempt counter and phase-namespaced idempotency keys.

Every write remains a KeeperHub call. Convoy sets no nonce, holds no key and implements no relayer.

## Tests

- kh-client: condition-met and condition-unmet parsing, measured flat wire shape, string condition
  value and retry idempotency.
- worker: all dependencies must be LANDED; deterministic registry dependency; unmet never executes;
  met executes once with the dependent item's actual target address, function, arguments and ABI;
  retries advance idempotency attempts; multiple dependencies do not duplicate; failed or
  completed-without-hash `commitAction` blocks both target paths.
- web: node count, dependency direction, chronological live colours, dashed/animated deferred
  edges, and live removal of waiting styling.

## Findings

- **G-35 MITIGATED:** a failed or missing-hash registry commit cannot proceed to the target write.
- **G-38 MITIGATED:** the check-and-execute wrapper now matches the sanitized live request/response.
- **G-39 OPEN:** concurrent `next build` and `next dev` use the same `.next` directory and can corrupt
  the active server's module graph. The cause is confirmed; automatic isolation is not implemented.
- The atomic KeeperHub guard checks the lowest declared dependency index. All dependencies remain
  load-bearing in the app-side LANDED gate; no multi-condition KeeperHub capability was invented.
