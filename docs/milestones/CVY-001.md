### Are the invariants falsifiable? — mutation test

A green invariant proves nothing unless a broken contract would turn it red. `committedCount += 1`
in `ConvoyRegistry.commitAction` was temporarily mutated to `+= 2` and the two counting invariants
re-run:

```
$ sed -i 's|r.committedCount += 1;|r.committedCount += 2;|' src/ConvoyRegistry.sol
$ FOUNDRY_INVARIANT_RUNS=20 forge test --match-test "invariant_idxMonotonic|invariant_committedCountMatches"
[FAIL: counter == accepted commits: 2 != 1]
[FAIL: every accepted commit must advance seq by exactly 1]
Suite result: FAILED. 0 passed; 2 failed; 0 skipped
```

Both caught it on the **first accepted commit**, shrunk to a two-call sequence. The mutation was
reverted and the registry re-verified token-identical to ARCHITECTURE §8 (1642 chars, both sides).

The test also drove a hardening: `ghostLastSeq` is now incremented by the handler itself
(`ghostLastSeq[runId] += 1`) and compared against the registry, rather than being assigned from a
registry read. The original form still caught the mutation — it compared the new counter against a
snapshot of the _previous_ one, which is a real cross-transaction delta — but the second assertion
in `invariant_idxMonotonic` (`ghostLastSeq == committedCount`) was comparing a mirror to the thing
it mirrored. With the counter independently derived, both halves are falsifiable. Re-verified: the
`+= 2` mutation still fails both invariants after the change.

G-13 is not theoretical. The first campaign, with uniformly random actor selection, reported
`accepted open/commit/seal: 4 0 0` over 32 calls — five green invariants at 1000 runs that had never
once reached a commit or a seal. The operator-biased handler brings that to `4 5 1`.

**What each invariant does and does not carry.** `invariant_committedCountMatches` and
`invariant_idxMonotonic` are the two that discriminate, proven by the mutation test in §4.
`invariant_noDoubleSeal` and `invariant_operatorIsOpener` guard properties the fuzzer reaches
routinely. `invariant_noCommitBeforeOpen` is the weakest of the five in a fuzz campaign: `openRun`
succeeds for any fresh runId regardless of caller, so all four runs are opened within the first
handful of calls and the pre-open branch is mostly dead by the time later checks run — what it
actually guards for most of the campaign is the post-open direction (an opened run never returns to
`None`). The pre-open property itself is pinned directly by the unit test
`test_commitAction_revertsNotOpen` and by `test_isCommitted_falseForUnopenedRun`.

## 8. Decisions recorded

`D-009 2026-08-03: MockRewardDistributor ships with no events and no access control` — Architecture
§8 names three functions and one requirement (genuine reverts); events, an owner and token transfers
are all additions to a frozen surface. The proof surface is `ConvoyRegistry`, which does emit.

`D-011 2026-08-03: ghost counters are derived by the handler, never assigned from a registry read,
and the counting invariants are mutation-tested` — see §4. Re-run the mutation whenever the handler's
ghost state is refactored.

`D-010 2026-08-03: the invariant handler biases its actor towards the run's operator, and reports
accepted-vs-rejected call counts` — see G-13. The campaign-non-empty assertion checks _calls driven_
rather than _calls accepted_, because the latter is not guaranteed by the fuzzer and a flaky CI check
is worse than no check; reachability is guaranteed by `test_handler_reachesEveryState` instead.
