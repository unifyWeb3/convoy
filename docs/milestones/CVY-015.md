# CVY-015 — Idempotency, Crash Resume, and Kill-Worker Proof

## Outcome

The production worker path now reconciles persisted KeeperHub executions before acting. An attempt
row is prepared before a write, the returned execution ID is persisted immediately, and recovery
polls that ID. If a process dies before the ID is recorded, the same persisted attempt number and
phase-folded idempotency key are replayed. No nonce is set and no private key enters Convoy.

The BullMQ phase handlers and `POST /api/runs` now use the existing `runBatch`/orchestrator path.
The API accepts only an existing persisted run ID and enqueues the deduplicated plan job. No second
orchestrator or unsupported product capability was introduced.

Review hardened the queue-start path: a fresh `PLANNING` run now reloads the persisted
`CRITIQUING` state before phase selection, API-enqueued jobs carry the same attempts/backoff policy
as the worker queue, the first persisted `runIdOnchain` wins concurrent OPEN recovery, and
serializable attempt preparation makes concurrent COMMIT/EXECUTE recovery converge on one durable
row without changing the frozen ledger schema.

The deterministic kill/restart proof uses a transport that throws during the first EXECUTE poll,
then resumes from the persisted execution ID. It proves one target broadcast, one transaction hash,
and one `ITEM_LANDED` event; the already-committed path is not resubmitted.

## Live Acceptance

Passed on Base Sepolia (`84532`) on 2026-08-09 with `CONVOY_EXECUTE_FANOUT=1` and one fresh
single-item run (`enableMarket(78)`). The worker was terminated with a real `SIGKILL` after the
EXECUTE KeeperHub response had been durably persisted and before status polling completed, then
restarted with the same production worker binary and environment.

- Run: `e0dd13db-1b60-484e-925c-9ad327463c9f`
- Onchain run ID: `0x1163f6451f294c41eaf1ddf6bc28a599b630affca9e6278e40224f4d28f1006b`
- COMMIT execution: `3ifaueblqpdora4ovw5fn` →
  `0x62a71e6669effe2cb899bd6a916c04482c80cba9e85a941fd32e789ecefccfc3`
- EXECUTE execution: `8bwrgf7yzrqb6b3k24y9w` →
  `0x280053932c3d20d5afdbcffc40a3319e7cf7ac33699c686b446ee85056c284cb`
- KeeperHub status re-read after restart returned `completed` with the identical EXECUTE hash.
- The recovered item reached `LANDED`, the run reached `SEALED_OK`, and the onchain target read
  `marketEnabled(78) == true`.
- The receipt for the recovered transaction returned status `0x1`.
- Duplicate proof: zero duplicate 32-byte transaction hashes across the ledger and zero duplicate
  hashes within the acceptance run. Three historical test-double COMMIT rows contain zero-length
  `bytea` values; they are invalid legacy artifacts, not transaction hashes, and were not rewritten.

The acceptance therefore proves the required same-execution recovery and no-duplicate broadcast
boundary without setting a nonce, holding a private key, or fabricating a retry/hash/failure.
